# Changelog

Every notable change to the flower workspace, newest first. The workspace shares
one version number and one release, so this is the changelog for all of it — the
scope on a bullet (`**core**`, `**ffi**`, `**tui**`) says which surface moved.
`flower-core` and `flower-ffi` go to crates.io; `flower-ratatui` and
`flower-tui` are `publish = false` and change under the same version number.

The `## Unreleased` region below is generated by `cargo xtask changelog --write`
from the commits since the last tag, and `cargo xtask release` cuts it into a
released section. Everything outside that region is handwritten and stays that
way — including a release intro, when a release wants a narrative rather than a
list. **Behavioural changes** is generated too, from `Behavioural-change:`
trailers on the commits themselves; write one on any commit a consumer would
notice after upgrading without editing a line of their own code.

`flower-core` **0.1.0 is on crates.io** — published by hand on 2026-08-17, at
`17e450f`, before the page projection existed. It was published without a `v*`
tag, so the tag-driven machinery below cannot see it: `cargo xtask changelog`
counts commits since the last tag, finds none, and lists the whole history as
unreleased. Read the region below as "since 0.1.0" and expect the earliest
entries to be things 0.1.0 already shipped.

The practical consequence is that **0.1.0 can never be reused**, tag or no tag —
a crates.io version number is burnt the moment it uploads. The next release is
0.2.0, which is also what the added public fields on `PageItem`/`Page` call for
on their own.

`flower-ffi` joins it on crates.io at that release — its view projection is
generic over the backend now, and an embedder with a `Backend` of its own needs
to depend on it rather than reimplement it. Its first upload is therefore 0.2.0,
skipping 0.1.0 entirely.

Commits predating any convention land in **Uncategorised — triage before
release** rather than being dropped; cutting a release wants a pass over that
bucket first. `docs/releasing.md` is how it is cut.

- Extract flower into a workspace: flower-core / flower-ratatui / flower-tui

Split the single crate into three, mirroring leaf core/widget/app tiers so the
editing logic is frontend-neutral ahead of a GPUI product frontend and a prov
integration:

- flower-core: the Model (owns fig::Editor), tree projection, format detection.
  No UI, no filesystem -- constructed from bytes; embedder owns the file. Tests
  moved here (inline fixture, no path coupling).
- flower-ratatui: a draw(frame, &Model, header) widget over flower-core.
- flower-tui: the flower binary -- file I/O + terminal event loop.

Behavior unchanged; all 4 core tests green, clippy clean. ([`e283b5e`](https://github.com/diaryx-org/flower/commit/e283b5ecb7afba60f16269476b939fdb1291e4bd))
- Make flower-core generic over a commit-sink Backend trait

Model no longer owns a fig::Editor directly. It builds path-addressed EditOps,
applies them through a Backend, and re-derives its view from Backend::to_value.
This is the seam the prov integration plugs into: a prov backend applies the
same ops through prov edit/mutate (maintaining inverse links, fixity, journal)
without Model knowing.

- backend.rs: Backend trait (apply / to_value / source), EditOp, BackendError,
  and FigBackend (the fig::Editor impl).
- model.rs: Model<B: Backend>; edits funnel through one commit() path.
- to_value yields the value tree, not just source, so an embed/prov backend can
  render the metadata region rather than the whole host file.

Behavior unchanged; 4 core tests green, clippy clean. ([`53b9d71`](https://github.com/diaryx-org/flower/commit/53b9d71073193569fabee6856136fc86cd2c0e1f))
